# generate-lesson-yaml

ドキュメントから**ハンズオン教材の中身**を組み立てるスキル。出力は 2 ファイル、
`lesson.yaml`（教材の骨格と本文）と `evidence.yaml`（その根拠となる逐語の引用）。

```
index.yaml（doc-index/v1・既存・読むだけ）
  +  ユーザーの要求
        ↓ ① 骨格を書く（事実は空・needs_facts だけ宣言）
     lesson.yaml (skeleton)
        ↓ ② needs_facts が指す少数のページだけ取得
     evidence.yaml   ← 逐語。ここは要約しない
        ↓ ③ 骨格に束縛
     lesson.yaml (filled)   ← origin と source_refs が全項目に付く
```

`lesson.yaml` は 2 回書かれる。1 回目は事実の空いた骨格、2 回目は evidence を束縛した完成形。
**ページの取得はこの 2 回の間でしか起きない。**

## このスキルが保証すること / しないこと

- **保証する — 追跡可能性。** 教材のどの部分が公式ドキュメントの記述で、どの部分をこのスキルが
  埋めたかが、項目ごとに `origin` で分かる。
- **保証しない — ビルドが通ること。** ビルドが通らない理由はさまざまであり、教材の内容に起因するものとは限らない。
  教材はドキュメントから生成した成果物のため、ビルドを保証するものではない。
- **要求しない — 特定の開発環境。** このスキルが前提にしてよいのは「ドキュメントを取得できる
  こと」だけ。ユーザーの環境で構築したビルドツールやエディタ拡張を前提にすると、共有したときの導入障壁になる。

## このスキルの範囲外

- **索引の作成。** `index.yaml` がなければ先に `generate-doc-index` を実行するようにユーザーへ回答する。
- **HTML の生成。** このスキルは `lesson.yaml` と `evidence.yaml` の生成のみ行う。

## 書き出し先

**一時ディレクトリではない安定した場所**に、1 リクエスト 1 ディレクトリで書く。
既定は `<workspace>/lessons/<topic>/` 配下の `lesson.yaml` と `evidence.yaml`。

最後に**絶対パス**を報告する。

## 手順

### ① 骨格を書く

1. **索引と要求を読む。** `index.yaml` の `groups` / `pages[].abstract` を要求と突き合わせ、
   関係しそうなページを絞る。この段階ではまだ 1 ページも取得しない。

2. **範囲を決める。** `scope.covers` に扱う範囲、`scope.excludes` に**意図的に外した**範囲を
   書く。要求より広げない。

3. **プロジェクトを設定する。** `project.name` / `project.stack` を決める。

4. **手順を並べ、各手順に `needs_facts` を書く。** `needs_facts` は「この手順を書くために
   ドキュメントから何を知る必要があるか」の宣言で、**この宣言がそのまま次段の取得指示になる**。
   ドキュメントの構造ではなくカリキュラムが取得を駆動するので、取得したのに使わないページが
   出ない。この時点で `files[].content` は空のまま。

### ② 事実を取得する

5. **`needs_facts` をページに割り付ける。** 索引の `path` を使う。**パスを推測しない** —
   索引が実在するパスを記録しているのは、生成時に URL を推測させないため。Apple の場合は
   JSON データエンドポイント（`developer.apple.com/tutorials/data/documentation/<path>.json`）
   を取得する。

6. **割り付いたページだけを取得する。** 索引に載っていないページが要るときは親を辿って
   一時的に取得する（索引には書き戻さない）。

7. **`evidence.yaml` を逐語で書く。** 粒度はページではなく**事実**。`needs_facts` の 1 宣言に1 fact が対応する。
   **ここだけは要約しない** — コードと宣言を言い換えた時点で、教材が
   ドキュメントから生成されたものである意味が消える。詳細は`references/evidence-yaml-schema.md`。

### ③ 束縛して完成させる

8. **`lesson.yaml` を埋める。** `files[].content` を書き、事実を主張するすべての項目に
   `origin` と `source_refs` を付ける。origin の 4 値と、値ごとに要求される `source_refs` /
   `origin_note` の規則は `references/lesson-yaml-schema.md` を参照。

9. **埋まらなかった事実があれば、末尾から切る。中抜きしない。**
   手順は積み上がっているので、途中の 1 手順を落とすと以降の手順が成立しない。取得しても
   該当する事実が見つからなかった場合は:

   - **末尾側の手順が埋まらない** → そこから後ろを丸ごと落とし、`scope.truncated: true` と
     `truncated_reason` / `unmet_facts` を書く。
   - **途中の手順が埋まらない** → その手前で切るか、その 1 手順を `origin: authored` として
     明示的に埋めて先へ進む。どちらを選んだかを `truncated_reason` か `origin_note` に残す。
     黙って埋めない。
   - **残る手順が 3 未満になる** → 教材として成立しないので**中止**し、どの事実が取れなかった
     かをユーザーに報告する。中途半端な教材を出さない。

10. **検算する。** 以下を全部通してから完了を報告する:

    - `source_refs` の参照先がすべて `evidence.yaml` に存在する（未参照の id なし）
    - `evidence.yaml` の全 fact がどこかから参照されている（未参照 fact は削除する。残って
      いるなら、取得が要求ではなくドキュメント構造に引きずられた証拠）
    - origin ごとの `source_refs` 件数と `origin_note` の有無が規則どおり
    - 全 `path` に `http(s)://` が含まれていない
    - `steps[].id` / `facts[].id` に重複がない

11. **報告する。** 絶対パス、手順数、fact 数、そして **origin の内訳**（`verbatim_from_doc` /
    `adapted` / `synthesized` / `authored` が何件ずつか）。`authored` の比率が教材の性質を
    そのまま表すので、これは毎回出す。

## ガードレール

- **`authored` を減らし、必ず見えるようにする。** この値が付く箇所はスキルが勝手に書いた箇所。
  増えるほど教材は書き手の一般知識に依存し、検証手段のない推測が混ざる。隠さない。
- **`scaffold` は粗く書く。** プロジェクト作成手順はほぼ確実に `authored` になる。詳細に
  書き込むほど特定のツールバージョンや UI に縛られ、画面が変わった瞬間に教材が壊れる。
- **`common_errors` はドキュメントに記載のあるものだけ。** 実行して確かめる手段を持たない以上、
  「よくある詰まり」を書き始めると推測が混ざる。スキーマ上 `source_ref` が必須なので、記載が
  なければ書けない。
- **`observe` 型の検証点を機械検証できるふりをしない。** 「検索結果に出る」のような確認は
  学習者にしか行えない。代わりに `see_also` で当該ページに戻れるようにする。
- **すべての `path` から `http(s)://` を落とす。** HTML生成時にはバリデーションスクリプトを実行して URL スキームを弾くが、この段階で落とすようにする。
- **スキーマを小さく保つ。** フィールドを足す前に、「これはドキュメントか要求から読んだ内容を
  運んでいるか、それともこのスキルがどう動いたかを説明しているだけか」を問う。後者は正当化が要る。
